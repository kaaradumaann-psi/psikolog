## 4. Migration

`supabase/migrations/20260925000002_p0_6_formulation_safety.sql` (209 satır). Toplam migration 9 → **10**.

**Adlandırma:** proje convention'ı çoğul snake_case (`clients`, `anamneses`, `appointments`,
`test_administrations`, `report_versions`). Önerilen `formulations` / `safety_plans` bu convention'a
zaten uyduğu için aynen kullanıldı.

**`formulations`:** `id` (pk, `gen_random_uuid()`) · `client_id` (→ `clients(id)` **ON DELETE CASCADE**) ·
`organization_id` (→ `organizations(id)` cascade) · `modality` (≤200) · `predisposing` /
`precipitating` / `perpetuating` / `protective` (≤4000) · `goals jsonb` (array, ≤256 KB) ·
`review_date date` · `created_by` (→ `profiles(id)` cascade) · `created_at` · `updated_at` ·
`unique (client_id)`.

**`safety_plans`:** `id` · `client_id` · `organization_id` · `warning_signs` · `coping` · `people` ·
`professionals` · `environment` · `reasons` (her biri ≤4000) · `created_by` · `created_at` ·
`updated_at` · `unique (client_id)`.

**Trigger'lar (mevcut fonksiyonlar yeniden kullanıldı, yeni fonksiyon yazılmadı):**
- `set_updated_at()` → `formulations_set_updated_at`, `safety_plans_set_updated_at`
- `log_audit_change()` → `formulations_audit`, `safety_plans_audit`
- `preserve_created_by()` (P0 §7) → `formulations_preserve_created_by`, `safety_plans_preserve_created_by`

**Audit:** `audit_logs_action_check` listesine 6 action eklendi
(`formulations_insert/update/delete`, `safety_plans_insert/update/delete`). Tablo **append-only kaldı**
(P0 §8'deki `revoke insert/update/delete from anon, authenticated` değişmedi).

**Yetkiler:** `revoke all … from anon` + `grant select, insert, update, delete … to authenticated`
— `documents`/`notes`/`appointments`/`tasks` ile aynı. `service_role` yok.

**Veri modeli genişletilmedi:** yalnızca `CaseFormulation` ve `SafetyPlan` tiplerinde zaten var olan
alanlar kolon oldu. Yeni alan icat edilmedi.

**Dokunulmayanlar:** hiçbir mevcut tablo/politika/veri değişmedi; **`20260925000001_p0_5_storage_object_isolation.sql` dosyasına dokunulmadı**; storage politikaları gevşetilmedi.

## 5. RLS

Temel kural uygulandı: **bir psikolog yalnızca kendi danışanının formülasyonuna ve güvenlik planına
erişebilir.** P0 §6'nın şekli birebir kopyalandı:

```sql
-- SELECT
public.is_admin()
or (public.is_org_admin() and public.is_org_member(organization_id))
or (public.is_org_member(organization_id) and created_by = auth.uid())
```

**Yeni gevşek `is_org_member()` politikası yazılmadı.** `notes`/`documents`'ın orijinal SELECT
politikasındaki `is_admin() or is_org_member(organization_id)` şekli (kurum içi çapraz okumaya izin
veren) **bilinçli olarak kullanılmadı**; P0 §6'nın sıkılaştırılmış hâli kullanıldı.

| İşlem | Politika |
|---|---|
| SELECT | `is_admin()` · `is_org_admin() AND is_org_member(org)` · `is_org_member(org) AND created_by = auth.uid()` |
| INSERT | `created_by = auth.uid() AND is_active_user() AND is_org_member(org) AND (is_psychologist() OR is_org_admin() OR is_admin()) AND exists(client aynı kurumda)` |
| UPDATE | using + with check: `is_admin() OR (is_org_member(org) AND (created_by = auth.uid() OR is_org_admin()))` |
| DELETE | using: `is_admin() OR (is_org_member(org) AND (created_by = auth.uid() OR is_org_admin()))` |

Admin / ORG_ADMIN davranışı mevcut sistemdeki gibi korundu.

Ek savunma: `preserve_created_by()` upsert ile sahiplik devrini engelliyor.

## 7. Mapping

Yerel modelde formülasyon ve güvenlik planı **danışan başına tek kayıt** (`clientId` ile anahtarlı,
kendi `id`'si yok). Bu yüzden:

```ts
formulationRowId(clientId) = deriveUuid('formulation', clientId)
safetyPlanRowId(clientId)  = deriveUuid('safety_plan',  clientId)
```

Deterministik id ⇒ tekrar gönderim aynı satırı upsert eder. `unique (client_id)` ikinci güvence.
Aynı desen `anamneses` için zaten kullanılıyordu (`deriveUuid('anamnesis', client.id)`).

Tüm alanlar iki yönde eşleniyor: `modality`, 4×4P alanı, `goals[]` (id/text/measure/status),
`reviewDate`; güvenlik planının 6 alanı. `text()` yardımcısı diğer mapper'larla aynı şekilde
trim + kontrol karakteri temizliği + uzunluk sınırı uyguluyor. Boş değerler `null` yazılıyor ve
okumada `''`'a dönüyor — mevcut sistem davranışıyla aynı.

`reviewDate` yalnızca `YYYY-MM-DD` ise yazılıyor; `date` kolonu okunurken `toDateOnly()` ile
normalize ediliyor (P0'da bulunan node-postgres/PostgREST farkı).

## 8. Sync

```
saveFormulation(item) → write(FORM_KEY) [cache] → pushCloud({entity:'formulation'}) → sync.enqueue
                      → repository.pushFormulation → db.upsert('formulations')
saveSafetyPlan(item)  → write(SAFETY_KEY) [cache] → pushCloud({entity:'safety'})   → …
```

Geri yükleme:
```
pullSnapshot() → repository.pullAll() → applyCloudPracticeSnapshot({formulations, safetyPlans})
               → rowToFormulation / rowToSafetyPlan → mergeByClientId → store → UI
```

- Yazılar mevcut **sıralı kuyruktan** geçiyor (`enqueue` + `flushWrites()`); yeni bir yol açılmadı.
- Başarısız yazı outbox'a düşüyor ve `psikolog:sync-error` ile bildiriliyor (mevcut mekanizma).
- `mergeByClientId` = `{...local, ...incoming}` ⇒ **cloud kazanır**, `mergeById` ile aynı birleşim
  semantiği.
- `pushLocalPracticeRecordsToCloud()` iki kaydı da itiyor ⇒ bootstrap'ta cihaz backlog'u buluta gidiyor.

`push()` içindeki outbox anahtarı `'id' in entry.record ? entry.record.id : entry.record.clientId`
— bu iki kaydın kendi `id`'si olmadığı için.
